# One shared codebase

The primary product and design target is the iPhone/iOS study experience. iPad and native Mac use the same SwiftUI screens, navigation, state and services, with mostly automatic adaptations. Prefer available space, text size and real capabilities over device names or operating-system checks. Improve the iPhone flow first; validate that its shared adaptations also work elsewhere.

The current implementation uses one SwiftUI app, `App/UsagiUnagiApp.swift`, for iPhone, iPad and native Mac. `App/UsagiUnagi.xcodeproj` has one multiplatform app scheme. Catalyst and the iPad compatibility destination are disabled. The main app, shared package and retained watch targets use Swift 6 language mode with the Xcode 27 / Swift 6.4 toolchain.

Automated validation has passed within the scopes recorded in [current tasks](TASKS.md); rendered usability and signed-device acceptance remain unfinished. The owner requested production changes first, then comparison with the original Tsurukame, then tests. Historical receipts apply only to their recorded sources. [The migration specification](Migration.md) defines storage and account-safety contracts.

## Ownership and storage

`StudyApplicationOwner`, held in SwiftUI state, coalesces startup before publishing services. `StudyAppAssembly` supplies the same account model, persistence actor, font/audio libraries, notification owner, subject/lesson settings, image caches and voice factory to every route. Windows share services rather than constructing another writer.

`StudyAppModel` owns account restoration, refresh, cancellation and observable account state. `StudyStore` commits decisions, completed submissions, notes and outbox changes atomically. Pausing a screen preserves its durable session; scene storage holds only transient answer drafts. The network layer distinguishes unsent work, attempted requests with uncertain replies, acknowledged work and explicit recovery. It never silently replays an uncertain answer or clears saved work on an error.

Synchronization and publication belong to the app. A canceled waiting view still receives cancellation, but the committed snapshot/profile publish together first; account/credential generation changes continue to fence that publication. Sign-in and reauthentication retain caller cancellation so a dismissed form cannot commit credentials.

Shared fetches belong to internal synchronous methods on the concrete SwiftData models: `CatalogRecord`, `AssignmentRecord`, `AccountRecord` and `MaterialRecord`. Their extensions live beside the current feature code, outside frozen V1 declarations. The store actor passes its existing `ModelContext`, for example `MaterialRecord.fetch(in: modelContext, accountID: accountID, subjectID: subjectID)`. Transactions, account/revision checks and network orchestration remain on that actor; public entry points return Sendable domain values. Prefer these direct model methods and native SwiftData APIs. Introduce another layer only for a concrete responsibility that existing models or the actor cannot express clearly.

iOS cold import reads the original database through SQLite3 in a read-only transaction, verifies stable account identity and persists an idempotent handoff before activating native services. Archived preference metadata/decoding is independent of the removed Settings UI and does not write defaults while reading. Original databases, media and credential compatibility are preserved. Regular application writes use SwiftData; the old FMDB writer and raw SQL diagnostic export have no production caller and are retired.

Production startup uses the owner-approved generation opener. It preserves a read-only source image, validates a separate candidate against physical schema metadata and complete values, durably selects that candidate, and retains its actor/lease for service ownership. The ten V1 model declarations preserve their original identities. Handoff values use typed equality so unordered preference Sets cannot falsely reject an equivalent store; session/catalog order stays significant. Disposable frozen base/WAL adoption, exact records, lease refusal, writes and abrupt-process reopens pass on Mac. Frozen base/WAL adoption, a note edit and same-process actor reopens also pass on the iPhone simulator; the WAL case preserves a seeded commit absent from the unchanged base DB. iOS fresh-process/abrupt-WAL and physical failure cases remain open. Historical nested decoders need independent freezing before a V2/property change. See the [implementation checkpoint](Implementation/2026-10-20-native-store-opening.md), [iPhone follow-up](Implementation/2026-10-21-frozen-ios-and-review-focus.md) and [migration specification](Migration.md).

Existing store images receive a read-only Core Data payload preflight before SwiftData property decoding. Public binary expression projections and the exact frozen model hashes let the existing generation owner validate all fifteen Codable fields without triggering SwiftData's fatal transformed-value decoder. Normal queries/writes remain on SwiftData models and the store actor. Selected-store matrices safely refuse 26 actual malformed-payload cases and five metadata/cache cases. Three damaged first-adoption inputs also refuse twice in fresh Mac processes, preserving original/retained images and all abandoned preparation artifacts; exact-state controls pass. Broader interruption/device/performance acceptance remains open. This adds no per-launch clone or storage service. See the [safeguard](Implementation/2026-10-21-adaptive-validation.md) and [expanded evidence](Implementation/2026-10-21-frozen-ios-and-review-focus.md).

The existing opener also passes real task cancellation at observed backend store-open events on Mac/iPhone. Preparation stays unselected, an existing selection stays byte-exact, original/retained data survives and a new caller can acquire the lease and restore the complete two-account state. The test observes public Core Data notifications and cancels a Swift task; no fault hook or second persistence owner is added. This covers those same-process event boundaries, while mid-copy/late-selection cancellation and process/power interruption remain separate gates.

## Study experience

Use standard SwiftUI adaptation directly: semantic toolbar actions, native search placement, form presentation sizing, `ViewThatFits`/adaptive grids and `AnyLayout` driven by the offered viewport and Dynamic Type. Avoid parallel phone/tablet/desktop feature flows, an `isMac` utility layer or a generic platform capability framework. A view should only need an OS branch when an actual API or supported service is unavailable; keep that boundary narrow and explain it below. Do not hide a removable condition inside a helper or sacrifice Japanese input, accessibility, keyboard behavior or offline study merely to reduce a count.

The remaining shared-UI OS conditions configure Japanese input, iOS keyboard traits, audio interruption, notification authorization/system Settings and activity prediction. They do not choose separate layouts or navigation flows. Keep these checks beside their unavailable APIs; replacing them with generic flags would add indirection without making the experience adapt better. Review new screens first at iPhone portrait width, then with larger text, the keyboard present, a short landscape viewport and freely resized windows.

Review layout defaults to stacked iPhone portrait content. A short, wide study viewport can put the question beside one answer column, retaining the input subtree and its focus owner. Window/keyboard resizing must not trigger an extra focus command. Form sheets, search and title display use the same declarations on all three platforms. Native lesson reordering uses the SwiftUI 27 container rather than separate desktop buttons and mobile edit mode.

One permanent review scroll surface contains progress, the question, answers and revealed information. Its content fills the offered height when it fits and grows when text/controls need more space; scrolling does not dismiss the answer keyboard. Embedded subject details return their existing content into that surface, while standalone details keep their own scroll owner. Lesson tiles use adaptive minimum widths and heights, with large-text meaning labels and selection actions allowed to grow. The picker and teaching strip retain full catalog subjects so image-only radicals render through the existing cached SVG view. Lesson quizzes keep system fonts; custom review-font settings remain available for reviews/practice.

Coverage's menu filters use their natural width in `ViewThatFits`, stacking when a horizontal row does not fit. Revealed Anki uses the existing menu's primary action and Return to open assessment; one shared action body keeps grading, deferring, exclusion and synonyms available without assigning default credit. The Japanese input adapter explicitly preserves locked text on Cut and routes Backspace to retry; editable deletion stays with the system field. These are local controls, not a new platform or input framework. Actual-field tests pass; rendered adaptive/menu/keyboard acceptance remains open.

`StudyRootView` owns one typed navigation stack and the Home, Practice and Statistics destinations. Review, lesson, catalog and settings behavior lives in shared views. WaniKani subject colors, system text styles, SF Symbols and native glass controls remain the visual basis. Layout adapts to available space; platform conditions belong at capability boundaries.

Main and watch app icons compile directly from the shared `Resources/UsagiUnagi.icon`. Both legacy app asset catalogs and their 37 unused files are retired; this also removes the old iOS-only catalog build reference. SF Symbols and Swift color definitions own the current screen styling. Font previews retain their separate shared-package resource catalog. Static default icon exports fit iPhone/watch masks, and the compiled Mac fallback stays byte-exact; on-device appearance remains a separate gate.

Reviews and extra study use the same grader/session engine. Native review actions include typed/Anki grading, correction, adding a meaning synonym with the corresponding correction in one transaction, exclusion, defer, wrap-up, previous-subject details and completed-subject summaries. Continuing after an incorrect answer can advance without revealing it. Ending early retains the completed-item summary while discarding unfinished session work. Character-specific soft errors use the grader's exact normalized UTF-16 ranges in a SwiftUI attributed-text hint. Physical input and keyboard shortcuts still need final acceptance.

Command-C and Command-A retain system Copy/Select All behavior; correction actions use Control-C/Control-A. Font actions preserve ordinary Tab and arrow-key focus/caret behavior. These intentional shortcut changes must be included in the original-app usability comparison.

The [original-flow source comparison](Implementation/2026-10-20-original-flow.md) restores lesson pronunciation, locked incorrect-answer editing, summary Return/current-level labels, independent search visibility, paged titles, Home study commands and the detail size preference. Home owns Command-L/R; Mac refresh uses Command-Shift-R. Actual keyboard dispatch, rendered layouts and native usability remain final acceptance work.

Voice views receive an app-owned capture factory. Opening Voice starts listening without another Start tap; a non-nil Apple asset installation request requires an explicit download, while a nil request proceeds without a redundant prompt. Recognition produces a reviewable transcript; readings containing non-kana characters, including digits, require explicit kana correction. Reading corrections reuse `StudyAnswerInput`, preserving iPhone romaji conversion/Japanese keyboard behavior and Mac native IME without another editor or OS layout branch. Japanese capture also requests native alternatives. `VoiceAnswerDraft` joins only recognizer-supplied kana in final audio order, limits each segment to three choices and the menu to six distinct combinations, and never consults an answer key or converts kanji. The shared native menu appears only when alternatives exist. Raw recognition changes only after an explicit choice/edit; Return dismisses correction focus without grading. Voice never changes the grading policy. Capture cleanup and a shared audio lease prevent recording/autoplay conflicts across windows. Real Mac file-fed recognition and model tests pass, but rendered menu behavior, physical microphone capture, human accuracy, latency, interruptions and audio routes remain device gates.

`SessionSummaryView` counts completed subjects, using each meaning/reading's first result. Missed items reopen shared subject details. Subject details use the shared original-conjugation vocabulary highlighter, optional attributed mnemonic artwork, hidden/locked-subject filtering and one revision-checked material editor. Font/audio catalogs and caches have one owner; shared default adapters preserve imported settings and media paths.

Statistics use Swift Charts for coverage, SRS and pace/focus scenarios with chronological backtesting. The bundled reference catalog includes cumulative Kanji Kentei levels 10–2 (including pre-2), school/Jōyō sets and estimated JLPT sets. Provenance and generation rules live in [resource sources](../Shared/Sources/StudyCore/Resources/SOURCES.md). Coverage is a character-scope measure, not an exam pass probability.

## Cross-device and platform services

Recent mistakes remain durable locally. One optional app-owned `StudyMistakeSync` projects the last 24 hours to Apple key-value storage as practice hints, fences observed account/quota/initial events, and performs bounded foreground reconciliation. Verified historical username binding/revocation is persisted in the existing handoff payload. KVS provides neither an atomic cross-device merge nor remote acknowledgement. Proper owner-controlled signing and a shared iOS/Mac namespace remain open; no signed delivery is claimed.

`StudyNotifications` and `StudyCompanionDelivery` read one typed account projection. Notification preference/permission intent is separate from delivery. The watch adapter retains the original packet keys, activation retry, latest pending absolute schedule and duplicate window. iOS background refresh uses Apple's asynchronous task-request API; a background or fixture launch does not request permission.

The watch settings and WidgetKit complications use SwiftUI. Reviews/Level remain a single global choice; the historical unavailable selection 2 is preserved. `WatchCompanionCache` retains the installed extension's `LastKnownData`/`DataSource` defaults and atomically mirrors one typed binary property-list snapshot into an App Group. The widget reads that file without starting transport or accessing the account store. Startup, accepted packets, selection changes and face migration publish before requesting a WidgetCenter reload. Connectivity background tasks stay retained through activation, pending-content drain and queued main-actor publication attempts. Count projections accumulate independent hourly buckets and expire at the existing deadline; they assume no subsequent reviews.

The watch retains Apple's documented incremental `WKHostingController` path. The existing WatchKit extension product inherits `_WKExtensionMain`; availability of SwiftUI `App` and `WKApplicationDelegateAdaptor` alone does not establish its launch handoff. The current Apple workout sample has already converted its active target to an application, so it is not proof for changing this extension's linker settings. No speculative entry-point, bundle-identity or container migration is applied. The [watch checkpoint](Implementation/2026-10-20-watch-swiftui.json) records the source and SDK evidence.

## Remaining non-SwiftUI boundaries

- The iOS Japanese answer field is a narrow UIKit adapter for keyboard-language selection, marked text, selection and caret behavior. It is not a second study screen. Removal requires equivalent native SwiftUI input behavior on physical devices.
- Image decoding, AVAudioSession, Keychain, notifications, background scheduling and WatchConnectivity are platform service APIs used by SwiftUI. Their platform-specific setup remains necessary.
- Radical SVG display uses Apple's SwiftUI WebView and the shared cached source. The SVGKit dependency is removed.
- The watch settings screen retains the three-line `WKHostingController` adapter and empty 18-line scene for its installed extension/defaults identity. WidgetKit owns complication rendering in all four accessory families; the original ClockKit class now only migrates installed faces. Shared-container access, signed face upgrades and physical delivery remain unvalidated. The final single-target watch lifecycle conversion is separate. The main iPhone/iPad/Mac app has no storyboard/controller host. See the [WidgetKit checkpoint](Implementation/2026-10-20-widgetkit.md).
- Historical account conversion still needs SQLite3 and generated Swift protobuf messages. These decode old files; SwiftData cannot directly interpret the original custom schema.

The old DEBUG UIKit host, duplicate controllers, fifteen iOS storyboards, generated navigation/assets wrappers, FMDB and associated dependency integration are being retired together. Three preexisting owner-edited legacy files remain untouched on disk and are excluded from targets. Old test sources still need their final-stage ports. No pass or final LOC/dependency acceptance follows from source deletion alone.

## Developer workflow

Mainboard owns dependency restoration, bounded Xcode operations, results/diagnostics, formatting, lint, Swift syntax rules and per-file source inventory. There is no app-local build driver. `mainboard analyze swift-inventory` reports physical/nonblank lines, source classifications, imports, platform conditions and placed migration signals; it does not infer target membership or safe deletion. CocoaPods/SwiftGen integration is removed; native Swift packages retain committed resolution.

Apple execution now retains readable JSON diagnostics beside each exact result bundle, including failed native runs. `analyze swift-compare` compares saved source inventories with category changes separate from byte changes. These reuse Mainboard's typed reports and atomic generated-file writer; routine edits use direct patches and existing formatters. Neither feature authenticates a supplied inventory or proves the compiler's exact source inputs. See the [workflow checkpoint](Implementation/2026-10-20-mainboard-reports.md).

Synthetic services remain in DEBUG-only acceptance fixtures, isolated from real credentials/cloud/permissions. XCTest remains appropriate for UI automation; domain and persistence tests use Swift Testing. Final work proceeds through implementation completion, original-app usability comparison, then test/Release/dependency/runtime gates. The detailed former adapter descriptions remain in Git at `4842707d`; immutable [validation receipts](Validation) retain their exact historical scope.
